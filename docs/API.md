# API contract

Base URL: `http://127.0.0.1:8000`. Interactive reference: `/docs`. Generated schema:
`/openapi.json`; a build snapshot is included as `docs/openapi.json`.

## Endpoints and authentication

| Method | Path | Authentication | Purpose |
|---|---|---|---|
| GET | `/health/live` | none | Process liveness only; does not recheck database readiness |
| GET | `/api/v1/sql-rag/schema` | bearer token | Live, permission-filtered approved metadata and logical relationships |
| POST | `/api/v1/sql-rag/query` | bearer token | Natural language to validated SQL to executed evidence and answer |
| GET | `/docs`, `/redoc`, `/openapi.json` | none | API documentation; no live schema or data |

All `/api/` routes authenticate before parsing the body. Tokens map to a fixed server-side
`sales` or `analyst` policy. Token values come from private `.env` settings, are compared using
constant-time digest comparisons, and must be distinct random secrets of at least 32 characters.
This is development authentication, not a JWT/OIDC login flow. Unknown/duplicate authorization
headers are rejected. No caller-provided role, SQL, connection URL, or permission override is accepted.

## Query request

```http
POST /api/v1/sql-rag/query
Content-Type: application/json
Authorization: Bearer <SALES_TOKEN>
```

```json
{"question": "Show the top 5 products by revenue", "max_rows": 100}
```

| Field | Type | Constraints |
|---|---|---|
| question | string, required | 3–1000 characters after trimming; no NUL/control characters except newline/tab |
| max_rows | integer, optional | Default 100; 1–1000; further capped by server MAX_ROWS (default 100) |

Unknown fields, booleans/numeric strings in `max_rows`, and non-string questions are rejected.
The UTF-8 HTTP body is capped at 16 KiB, including chunked requests. There is no session memory
or conversational follow-up resolution in this version; each question must stand alone.

## Query response

Example below illustrates the **synthetic test fixture**, not results from your full Olist data:

```json
{
  "request_id": "08c49df6-5ab1-4cf1-b86b-ec6f452c69ae",
  "answer": "Returned 3 rows. First row: product_id = \"p1\"; revenue = \"300.00\".",
  "evidence": {
    "sql": "SELECT i.product_id, SUM(i.price) AS revenue FROM analytics.order_items AS i JOIN analytics.orders AS o ON i.order_id = o.order_id WHERE o.order_status = 'delivered' GROUP BY i.product_id ORDER BY revenue DESC, i.product_id LIMIT 5",
    "source_views": ["analytics.order_items", "analytics.orders"],
    "columns": ["product_id", "revenue"],
    "rows": [
      {"product_id": "p1", "revenue": "300.00"},
      {"product_id": "p2", "revenue": "50.00"},
      {"product_id": "p3", "revenue": "25.00"}
    ],
    "row_count": 3,
    "row_limit": 100,
    "truncated": false
  },
  "metadata": {
    "strategy": "placeholder",
    "intent": "top_products_by_revenue",
    "elapsed_ms": 12,
    "warnings": ["Revenue is item price on delivered orders in BRL, excluding freight; months use purchase dates."]
  }
}
```

The example UUID and duration are illustrative. Actual IDs and timing are generated per request.
Decimal/currency values serialize as strings to preserve precision. Dates/timestamps serialize in ISO
format; Olist purchase timestamps have no timezone and the service does not invent one. Null remains
JSON null. Counts remain integers. Averages over no rows can return null; the answer reports that value.

`evidence.sql` is the canonical **executed** SQL, including the enforced limit. To detect truncation,
the executor may fetch one extra row: `LIMIT min(candidate_limit, effective_max_rows + 1)`.
Only `effective_max_rows` rows enter the response. A candidate's smaller top-N limit is respected.
`truncated` means an extra row was observed, not that the complete match count is known.
No independent COUNT query is run. Results without ORDER BY have no guaranteed order.

`metadata.strategy` is `placeholder` or `api`; strategy is configured server-side.
`metadata.intent` is a placeholder intent identifier or `model_generated`.
The answer is deterministic text based on returned evidence, not a second model call.
SQL evidence is authorized data for the caller; do not expose responses to other users.

Every response includes `X-Request-ID`, `Cache-Control: no-store`, and
`X-Content-Type-Options: nosniff`. The request ID is generated by the server, never taken from a
caller header. Standard request/endpoint failures use:

```json
{
  "request_id": "08c49df6-5ab1-4cf1-b86b-ec6f452c69ae",
  "error": {"code": "SQL_REJECTED", "message": "The generated query does not satisfy the read-only SQL policy."}
}
```

## Error codes

| HTTP | Code | Meaning |
|---|---|---|
| 401 | UNAUTHORIZED | Missing/invalid token; includes WWW-Authenticate: Bearer |
| 403 | FORBIDDEN | Intent or resource is outside caller policy |
| 413 | REQUEST_TOO_LARGE | Body exceeds 16 KiB |
| 422 | INVALID_REQUEST | JSON or request model invalid |
| 422 | UNSUPPORTED_QUESTION | No supported placeholder intent/model refusal |
| 422 | SQL_REJECTED | Generated SQL violates syntax/structure/object/function/relationship policy |
| 422 | QUERY_EXECUTION_FAILED | PostgreSQL rejected query semantics/types; raw driver message withheld |
| 422 | RESULT_TOO_LARGE | A value exceeds 2000 characters or normalized rows exceed 1 MB |
| 429 | BUSY | Per-process concurrent query capacity exhausted |
| 500 | INTERNAL_ERROR | Unexpected error; no traceback or credentials returned |
| 502 | GENERATOR_UNAVAILABLE | Provider timeout/error/malformed/truncated/oversized response |
| 502 | RESULT_INVALID | Non-finite/unsupported values or mismatched result structure |
| 503 | DATABASE_UNAVAILABLE | Connectivity/pool failure |
| 503 | SCHEMA_UNAVAILABLE | Missing or changed approved metadata |
| 504 | QUERY_TIMEOUT | Statement/lock execution budget exceeded |
| varies | HTTP_ERROR | Unknown route or unsupported HTTP method |

Startup rejects unsafe database credentials/version/grants before serving requests. The terminal
message is intentionally generic; run the documented permission checks for operator diagnosis.
Unauthorized generated table/column references use generic `SQL_REJECTED` rather than confirming
the existence of a hidden object.

## Supported placeholder wording

Matching ignores case, repeated whitespace, and trailing `?`, `.`, `!`. Supported complete phrases:

- `[Show [the ]]top N products by revenue` where N is 1–100; square brackets indicate optional words.
- `monthly revenue`, `show monthly revenue`, `show the monthly revenue`.
- `how many orders are there`, `total orders`, `count orders`.
- `orders by status`, `show orders by status`, `count orders by status`.
- `average review score`, `show average review score`, `what is the average review score` (analyst only).

API mode accepts broader wording but its generated SQL must remain inside the documented SQL subset.
Safety validation cannot prove a model's business interpretation. Check SQL and source definitions.
